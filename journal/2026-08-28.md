### A wrong diagnosis, corrected the same night

I reported to the founder that the board had under-reported **40 points** across
four rooms, based on `host/debrief.js` printing *"pts AND ITS OWN LANES
DISAGREE"*. **That was wrong and the board was never short.**

`debrief.js` reads the ARCHIVE — a snapshot the runner writes at one instant —
and the runner updates `pts` and the lane fields at slightly different moments.
Every drifted row had already reconciled in the live player doc: Dog Bird's
archive held `caughtPts=75` with `pts=390`; the live row holds `caughtSrv=90`,
which is 390 exactly.

Fixed by making the detector finish the job it starts: it now reads the live
row and says either *"settled live at 390 — the archive was taken mid-grade"*
or *"STILL DISAGREES LIVE — THIS ONE IS REAL."* A detector that cannot tell a
stale snapshot from a live fault guarantees the next real one gets dismissed.

### Season scoring — the founder's number one, and it was two faults

> "fix the season scoring first thing tomorrow"
> "I am on as two times and my points should be 105 but its 75"

**Fault one: `MAXPTS` was a `const`.** Worked out once at page load from
whatever night was built in — 600 + 400 from basketball — and never again.
`sportTotals()` exists *precisely* because `NR`, `CATCH_PTS`, `PRED_MAX` and
`LIVE_MAX` all had this bug and were fixed together. Its own comment reads
*"Leaving any of them behind is this codebase's whole disease."* MAXPTS was
left behind. It is the fifth entry in that function now.

The caught cap is also no longer gated on `lean()`. LEAN empties `CATCHES` — the
watchlist — correctly. **Caught It is a different feature**: the runner fires it
server-side in every hosted room whatever LEAN says on the phone. All five lean
rooms paid caught points last night (90, 15, 10, 10). A denominator that leaves
out a lane the numerator counts is a wrong total.

**Fault two, and the expensive one: an unscored room could EVICT a scored one.**

`score` was a percentage for a row with a ceiling and RAW POINTS for a row
without, and the two were compared with `>`. A legacy row carrying 150 raw
points beat a real room worth 45% — and then contributed **nothing**, because
the season sums `pct` and its pct is null. The row with no denominator did not
merely fail to count. It threw out the row that would have.

That is "150 points, SEASON PTS 0", exactly.

The comparison now happens in one unit: any scorable row beats any unscored one
whatever the raw numbers say; two scorable rows compare on pct; a night with
nothing scorable keeps its best raw row so the Board can still show it and say
honestly that it has no ceiling.

`qa/season.js` grew four checks for it. The suite tested a legacy row ALONE and
never one sharing a night with a real one, which is the whole gap. Observed
failing against the unfixed file before being believed:

### The gate earned its keep twice

Two suites went red on the overnight work, and both were correct to.

**`feed-path.js`** sliced the `const PATHS` literal out of `build-slate.js`
with a regex. The literal moved to `host/leagues.js`, so it parsed 0 leagues
and failed. Pointed at the new owner, and given a new check: every consumer
must READ the owner rather than keep a copy, so a fifth table appearing in
`host/` is caught rather than invisible. **8 checks → 21.**

**`spanish.js`** found the more interesting one. It reported two visible
strings with no Spanish:

    "OUT OF 1100"
    "…Max score: 1100. Post your result card…"

The dictionary held `"OUT OF 1000":"DE 1000"` — **the ceiling written into
the translation.** That was only ever right for basketball, so a Spanish
player in a baseball room (1300) or a soccer room (940) already read an
English line where a Spanish one belonged. Nobody had seen it because the
coverage walk loads the default sport, which is basketball: the one case that
worked was the only case measured. Making MAXPTS per-sport is what surfaced
it — the English changed to the true number and the baked key stopped
matching at all.

Fixed with `I18N_PATTERNS`, the anchored-regex list `applyLang()` already
falls through to, so the number is carried rather than frozen. Verified in a
browser at `?lang=es`: `OUT OF 1100 → DE 1100`, and the rules paragraph
translates in full.

**And then the test itself was wrong.** `spanish.js` asked "is this string a
key in the dictionary?" while `applyLang()` asks a different question — it
falls through to the patterns. So every pattern-translated string was being
counted as untranslated. It had never bitten because no patterned string was
on a walked screen. A coverage check that does not model the thing it measures
reports finished work as outstanding, and the fix for THAT is to raise
`--max`, which quietly blinds it to the real gaps.

It now mirrors `applyLang()` — and deliberately reads `I18N_PATTERNS.es`
rather than `I18N_PATTERNS[VX.lang]`, because this walk never switches the
page, so `VX.lang` is still `'en'` and keying on it returns an empty list.
That is the same silent-no-op shape `applyLang()` records in its own comment.

Sabotage-tested: with the pattern list renamed away, the check goes RED on
exactly those two strings. Widened, not weakened.

**A gap left open on purpose.** The rules paragraph is built as
`SPORT.ruleScore + " Max score: N. Post your result card…"`, and none of the
five `ruleScore` sentences has a Spanish entry of its own — the dictionary
only ever held basketball's CONCATENATED version. So that paragraph is
English in four sports out of five, and it has been for as long as Spanish
has been live. `spanish.js` cannot see it because the walk loads the default
sport.

Not fixed tonight, deliberately. Translating four paragraphs of product copy
unreviewed, at midnight, against a voice rule that says "sound human, not AI",
is how you ship four sentences nobody can vouch for. It needs either a
reviewed translation or the paragraph restructured so the sport sentence and
the tail are separately translatable. Written down so it is a decision rather
than a thing nobody noticed.
